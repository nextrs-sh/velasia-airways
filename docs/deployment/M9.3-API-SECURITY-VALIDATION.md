# M9.3 API security: service token and metrics authorization

| Item                                                                | Status (2026-11-26)                                 |
| ------------------------------------------------------------------- | --------------------------------------------------- |
| API enforcement code, storefront header, NextRS `--js-env` plumbing | Implemented since M8/M9; tests pass                 |
| Constant-time metrics bearer checks (API and storefront)            | **Implemented in M9.3, tested locally**             |
| Shared variables `RETAILING_API_SERVICE_TOKEN`, `METRICS_TOKEN`     | Not created (owner, outside Git)                    |
| Stage 2 `auth-clients.ts` (both storefronts)                        | **Proposed**; live read-only plan passes the gate   |
| Stage 3 `auth-enforce.ts` (API)                                     | **Proposed, blocked** until stages 1 and 2 are live |
| Enforcement on Railway                                              | Not deployed, not verified                          |

Production today: no token anywhere. The API answers every caller on the private network and
its `/metrics` is open there (it has no public domain). The storefronts' `/api/internal/metrics`
is blocked by the proxy in the Compose setup, but on Railway the storefronts are served
directly: **verified 2026-11-26, both public domains answer `/api/internal/metrics` with 200 and
Prometheus text** (process and request metrics, no personal data). Stage 2 closes it.

## What the code does

| Component                                 | Without the variable | With it                                                                                                                                                                      |
| ----------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API `RETAILING_API_SERVICE_TOKEN` (≥ 32)  | answers everyone     | every path except `/health`, `/health/live`, `/health/ready` needs `x-velasia-service-token`; 401 `UNAUTHENTICATED`. SHA-256 digests compared with `timingSafeEqual`         |
| API `METRICS_TOKEN` (≥ 16)                | `/metrics` open      | `/metrics` also needs `Authorization: Bearer …` (M9.3: digests + `timingSafeEqual`, was `!==`)                                                                               |
| Storefronts `RETAILING_API_SERVICE_TOKEN` | no header            | sent server-side on every API call; NextRS gets it through `--js-env` only when set (`docker/nextrs/start.sh`)                                                               |
| Storefronts `METRICS_TOKEN`               | route open           | bearer required (M9.3: `bearerMatches`, a full-length comparison in plain JavaScript, because the same code runs on NextRS's V8, where `timingSafeEqual` is not validated)   |
| Browser, image layers, logs               | never see either     | no `NEXT_PUBLIC_` name; no secret-named `ARG` (`pnpm railway:check`); build stages set the token empty; logs say `serviceToken: required/off`; 401 bodies never echo a token |

Tests: `apps/retailing-api/test/m8-service-auth.test.ts`, `m9-auth-rollout.test.ts` (stage
order, open health probes, metrics needing both tokens, empty = unset, no echo),
`m7-observability.test.ts` (metrics bearer), `apps/web/test/m8-service-token.test.ts` (header
sent), `apps/web/test/m9-3-metrics-auth.test.ts` (M9.3: 13 cases, wrong/short/long/lowercase
schemes refused, never echoed). `scripts/railway/m9-3-stages.test.mjs`: tokens are only ever
`sharedReference`s, on both storefronts or neither; a literal value fails the rules.

## Rollout

**0. Generate** on the owner's machine, never pasted into chat, tickets, files or CI logs:
`openssl rand -hex 32` (service token) and `openssl rand -hex 24` (metrics token).

**1. Store** as project shared variables in `production` (dashboard → Project Settings →
Shared Variables; sealed if offered). Redeploys nothing. The stage 2 and 3 plans reference them
by name; plan them only after they exist.

**2. Clients (stage 2, `auth-clients.ts`)**: both storefronts reference both tokens. Redeploys
both storefronts (environment only). The API still ignores the header (tested). Verify:

- `/api/internal/health/ready` 200 on both domains;
- flight search, `/api/flights`, `/api/offers`, a Server Action (shopping step) and a read-only
  booking lookup work on both;
- `/api/internal/metrics` without a bearer → 401 on both, with it → 200 (from an owner shell);
- the Node.js and NextRS startup logs never print the values.

**3. Enforcement (stage 3, `auth-enforce.ts`)**, only after stage 1 (the redeploy must not lose
data) and stage 2 are verified. Redeploys the API (about 1–3 minutes). Verify:

- startup log `serviceToken: required`;
- both storefronts ready and the checks of step 2 pass (they send the token);
- from inside the private network (a temporary runner, or the owner's `railway ssh` into a
  storefront): `/v1/airline` without the header → 401, with a wrong one → 401, with the right
  one → 200; `/health/ready` without any header → 200 (Railway's health check);
- `/metrics` with only the service token → 401; with both → 200;
- no response body contains a token.

**4. Benchmark runner**: its variables reference the same shared variables
(`${{shared.RETAILING_API_SERVICE_TOKEN}}`, `${{shared.METRICS_TOKEN}}`). `api-gate.mjs`,
`prewarm.mjs` and `scrape-in-container.cjs` read them from the environment and never print
them. `/metrics` stays private: no public domain for the API, ever.

## Rollback

Each is its own reviewed proposal, and none touches TalaDB or the volume:

| Undo                          | How                                                                                                                                                             | Redeploys        |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| API enforcement (stage 3)     | Remove the two references from the API (`variable.delete` × 2, `allowDestructive: true` with the reason). The storefronts keep sending a header the API ignores | API              |
| Metrics authorization only    | Remove `METRICS_TOKEN` from the service concerned. Its metrics become open again (private network for the API; public for a storefront)                         | that service     |
| Client distribution (stage 2) | Remove the four storefront references. **Only after stage 3 is rolled back**, or every API call gets 401                                                        | both storefronts |
| A leaked token                | Change the shared variable's value: every referencing service redeploys (no guaranteed order: a few failed requests while the API and storefronts disagree)     | all referencing  |

## Findings

- Before stage 2, the storefronts' `/api/internal/metrics` is publicly reachable on Railway
  (above). Stage 2 closes it; it can be applied before the persistence stage.
- Rotation without failed requests needs the API to accept two tokens during the overlap.
  Not implemented.
