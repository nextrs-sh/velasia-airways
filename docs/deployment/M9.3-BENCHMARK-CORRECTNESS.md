# M9.3 benchmark correctness: business time, real time, and the offer cache

**Status: implemented and tested locally.** Not deployed: production runs the pre-M9.3 API
(and has no `VELASIA_TODAY`, so its clock is not pinned today).

## The defect (fixed)

`VELASIA_TODAY` pinned the API's only clock: `clock.now()` returned midnight of that day,
always ([known issue](known-issue-pinned-clock-offer-expiry.md)). Everything time-based froze:
the 60 s offer reuse window, the 15-minute offer validity, shopping-session idle and maximum
life, checkout holds, servicing claims, account sessions and the stores' sweeps. On a pinned
deployment an offer created once was handed out for the life of the process, and a hold
created before a restart never ended after it.

## The fix: two clocks, one interface (`apps/retailing-api/src/clock.ts`)

| Method          | Meaning                                                                                               | Pinned (`VELASIA_TODAY`)    | Unpinned           |
| --------------- | ----------------------------------------------------------------------------------------------------- | --------------------------- | ------------------ |
| `today()`       | business date                                                                                         | the pinned date             | Manila date of now |
| `businessNow()` | business instant: sales cut-off, departure, change/cancel/seat/extras windows, upcoming vs past trips | midnight of the pinned date | `Date.now()`       |
| `now()`         | real time: every expiry, TTL and stored or displayed timestamp (`serverTime`, `expiresAt`)            | `Date.now()` (never pinned) | `Date.now()`       |

Unpinned, both are the same instant, so production behaviour without `VELASIA_TODAY` is
unchanged. Each `clock.now()` use was classified: `flights.ts` (search, availability, fare
calendar, "from" fares), `offer-engine.ts` (`itineraryProblem`), seat maps, servicing quotes
(change, cancel, seat and extras windows) and the account trip list moved to business time;
everything else (offers, sessions, holds, claims, the ledger, account sessions, sweeps, quote
validity) stays on `now()`, which is now real. Scenario offsets (`offer-expired`,
`session-expired`, `hold-expired`) shift both, as elapsed time does on the unpinned clock.

Real time is wall-clock epoch milliseconds, not a monotonic clock: holds, shopping sessions and
account sessions are persisted and compared again after a restart, and offer expiry is shown
to clients next to `serverTime`. A monotonic reading restarts with the process and cannot be
compared with a stored value. A wall-clock step only shifts the windows open at that moment. In
the browser nothing changes: the storefront derives remaining time from `expiresAt − serverTime`,
both API values.

### Tests (`apps/retailing-api/test/m9-3-clock.test.ts`, no sleeps, no fake timers)

Real time comes from a value the test moves (`createClock(TODAY, () => real)`):

1. pinned: `today()` and `businessNow()` fixed while `now()` moves; unpinned: all follow real time
   and the date rolls over at Manila midnight; the default real source is the system clock;
2. flight search for the pinned day is identical after 10 hours of real time (no flight slips
   past the sales cut-off);
3. offers are reused at +59 s and new at +61 s; a new window starts from the new offers;
   `serverTime` is real; `expiresAt` = real time + 15 minutes;
4. an offer is `AVAILABLE` at 15 min − 1 ms and `EXPIRED` at 15 min, and never handed out again;
5. checkout holds expire after 10 minutes of real time;
6. restart: a shopping session survives a restart inside its idle window and is expired after
   31 minutes of real time across a restart (business date unchanged); offers never survive a
   restart (memory only), and a fresh process creates new ones;
7. created offers are counted even when a sweep of expired ones keeps the store size flat.

Existing tests that used `clock.now()` as the business instant now call `businessNow()`. Two
process-level crash tests moved `VELASIA_TODAY` forward a day to make a hold or claim expire,
which only worked because of the defect; they now age the stored expiries (`elapseWhileDown`,
"down for a day of real time").

## Consequence for the benchmark

A pre-warmed offer cache now stays warm for at most one 60 s reuse window. A series of 120 s
runs cannot keep it warm, so the second runtime of a pair can meet a different cache state than
the first. Decisions for M9.3 (`benchmarks/railway/`):

| Workload                                                                                        | Paired comparison                                                                                                                                              |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `static-assets`, `rsc`                                                                          | Allowed: they do not depend on the API's offer cache (series 1 measured them)                                                                                  |
| `flight-search`, `route-handler`, `home`, `destination`, `cached`, `manage-booking`, `my-trips` | Allowed only when the API gate shows comparable shared-API conditions for both runs: idle baseline, same process, no writes, **no offers or sessions created** |
| `offers`, `comparison`                                                                          | **Refused** by `pair.mjs` (`OFFER_CACHE_WORKLOADS`): their cache state cannot be made equal for both runtimes                                                  |

The gate itself was also wrong after the fix: it inferred "offers created" from the change in
`velasia_memory_store_entries{store="offers"}`. With real-time expiry, the write that creates
offers also sweeps expired ones, so a run could create N offers while N expired and show a
change of 0. The API now exports `velasia_memory_store_created_total{store="offers"|"sessions"}`
(monotonic per process), the gate counts from it, requires it in every scrape (an older API
fails closed), and treats a decrease without a restart as a broken source. Tests:
`gate-lib.test.mjs` (a sweep hiding creation is still counted; missing counter → invalid;
decrease → invalid), `pair-lib.test.mjs` (offer workloads refused). The comparability rules
were not loosened anywhere. `prewarm.mjs` is now a diagnostic only.

The first cloud series (`RAILWAY-CLOUD-BENCHMARK-REPORT.md`, `results/2026-11-25-series-1`) is
unchanged historical evidence: `static-assets` and `rsc` against the pre-M9.3 deployment, with an
unpinned API that created no offers during those runs.

## Offer-cache experiments (a later, isolated environment)

What a fair offer or fare-comparison benchmark needs, none of it available in this milestone:

- **Separate equal APIs**: one API instance (and volume) per storefront, same image, same seed,
  same `VELASIA_TODAY`, so neither runtime warms the other's cache. Compare like with like.
- **Cold-cache runs**: restart each API (empty offer store), then run; every request creates
  offers. Measures storefront + offer creation.
- **Warm-cache runs** with a controlled window: warm, then run for less than the 60 s reuse
  window (or with a test-only, environment-set reuse window long enough for the run, on both
  APIs alike), and verify with `velasia_memory_store_created_total` that the run created nothing.
- **Synchronized alternatives on a shared API**: cool down past the 60 s window plus the store's
  grace before each run so both start cold, and require equal `offersCreated` per run. Only
  comparable if the two counts match.

Any of these must report which state it measured, and must not be reported together with the
read-only workloads.
