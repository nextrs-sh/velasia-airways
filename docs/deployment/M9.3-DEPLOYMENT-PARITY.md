# M9.3 deployment parity

A Node.js-versus-NextRS comparison is only fair while both storefronts run the same commit, the
same Next.js and the pinned NextRS release, with equal limits, in one region, one replica each,
against the same API, and nothing redeploys during a series.

`pnpm railway:deployments` on the live environment: **parity OK**.

| Service                  | Status  | Commit    | Region | Replicas | Active deployments |
| ------------------------ | ------- | --------- | ------ | -------- | ------------------ |
| `@velasia/web`           | SUCCESS | `69a77c2` | iad    | 1        | 1                  |
| `@velasia/web-nextrs`    | SUCCESS | `69a77c2` | iad    | 1        | 1                  |
| `@velasia/retailing-api` | SUCCESS | `69a77c2` | iad    | 1        | 1                  |

Also unchanged since M9.2: both storefronts build with Next.js 16.4.6; NextRS is
`@nextrs/cli@0.1.0-rc.2` (`docker/nextrs/package.json`); no `limitOverride` (plan defaults, 2
vCPU / 1 GB, equal by construction); same API private URL; storefront environments equal apart
from the per-runtime variables (`SITE_URL`, `RAILWAY_DOCKERFILE_PATH`, `NEXTRS_NET_ALLOW_ADDR`),
which `pnpm railway:check` enforces.

Not equal: the watch patterns. Node.js watches `/apps/web/**`, NextRS nothing (every change).
A merge touching only `packages/` or `apps/retailing-api/` rebuilds NextRS and not Node.js. This
happened in M9.1 (two different build fingerprints) and is what stage 5 fixes.

## The check: `pnpm railway:deployments`

Read-only (`railway status --json`). Fails (exit 1) unless:

- each service has exactly one active deployment, it is the latest one, its status is
  `SUCCESS`, and nothing is building or deploying;
- both storefronts run the same commit, and with `--expect-sha <commit>` the approved one;
- every service is in `iad` with one replica;
- with `--compare <snapshot>`, no deployment ID or image digest changed since that snapshot.

`--save` writes the snapshot (deployment IDs: keep it in `.railway/evidence/`, gitignored).
`--deployments-out <file> --cpu 2 --memory-bytes 1073741824` writes the `DEPLOYMENTS` file that
`pair.mjs` requires, only when parity holds (`pair-lib.mjs` checks it again per pair:
"storefronts run different commits", limits, region, NextRS version). The API may run an older
commit than the storefronts (its watch patterns skip storefront-only changes): it is recorded,
not required to match. Tests: `scripts/railway/deployments-lib.test.mjs` (revision mismatch,
approved-commit mismatch, in-progress/failed/overlapping deployments, region, replicas, a
redeploy between two snapshots).

## Release procedure for a benchmark series

1. CI green on the commit to benchmark; it is on `main`.
2. **Merge freeze on `main`** for the whole series (nothing merged; see the
   [release readiness](M9.3-RAILWAY-RELEASE-READINESS.md#before-anything-merging-is-a-production-operation)
   doc for why the dashboard "disconnect" is not used while IaC stages are pending).
3. `pnpm railway:deployments --expect-sha <commit> --save …/series-start.json
--deployments-out …/deployments.json --cpu 2 --memory-bytes 1073741824` → OK.
4. Run the series (`pair.mjs` also fingerprints each storefront's build before and after every
   pair).
5. `pnpm railway:deployments --compare …/series-start.json` → OK, or the whole series is void.

## Stage 5: `deploy-policy.ts` (proposed)

`checkSuites: true` (Railway's "wait for CI") on all three services, and identical storefront
watch patterns covering everything either image is built from (`apps/web`, `apps/retailing-api`
for the build-time API, `packages`, both Dockerfiles, `docker/nextrs`, the workspace manifests
and lockfile). The API watches what `docker/Dockerfile.api` copies. Live plan: 6
`resource.update` entries, only `source.checkSuites` and `build.watchPatterns` (the gate refuses
any other field). It does not stop autodeploys: the merge freeze remains the control during a
series. After it, the deploy-policy warning in `pnpm railway:check` becomes a failure if the
storefront patterns ever differ again.

## NextRS outbound allowlist (stage 4, separate and optional)

Live: `fd12::/16,10.0.0.0/8`. Proposed: `fd12::/16,10.128.0.0/9` (one `variable.set`, NextRS
redeploy). Rechecked 2026-11-26: the API's latest answers in NextRS's DNS log are
`10.137.93.22` and `fd12:382f:2f26:1:3000:1b6:5a89:5d16`, both inside the proposal; all seven
addresses seen since 2026-11-25 are inside `10.128.0.0/9` and `fd12:382f:2f26:1::/64`. Railway
documents no private IPv4 range, and the API moves on every redeploy: stage 1 and stage 3
redeploy it. So: apply stage 4 only **after** stages 1 and 3, re-read the address first
(`railway logs -s @velasia/web-nextrs --dns`), add it to `OBSERVED_API_ADDRESSES`, and keep
the rollback (the old value) ready. The origin restriction is unchanged:
`--net-allow` stays the API's origin only (`docker/nextrs/start.sh`), so no other private
service becomes reachable.
