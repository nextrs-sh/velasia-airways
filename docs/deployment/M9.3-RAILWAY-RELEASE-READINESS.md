(see [persistence](M9.3-TALADB-PERSISTENCE-VALIDATION.md#railway-verification-2026-11-26)) and folded

## Before anything: merging is a production operation

GitHub autodeploy is on for all three services (`main`, no "wait for CI"):

- the API redeploys on any change under `apps/retailing-api/**` (Railpack, ephemeral disk:
  that resets its TalaDB);
- Node.js redeploys on changes under `apps/web/**`;
- NextRS has no watch patterns: it redeploys on **every** merge.

This branch changes all three areas. **Merging it redeploys all three services** from the
merge commit, with the API still on its old Railpack configuration (a merge never applies
`.railway/railway.ts`). That resets the API's ephemeral database (disposable, by owner
decision), but it is still a production change, so it needs its own approval.

**Recommended: make the merge a deliberate, approved event, then freeze `main`.**

1. Approve "merge M9.3" as a production operation: expected effect = one redeploy of each
   service from the same commit, about 1–3 minutes of API downtime, demo data reset.
2. Merge the PRs in one window, A → B → C → D (A and D share `railway.ts`), after CI is green
   on each. Then check: `pnpm railway:deployments --expect-sha <merge commit>` → OK (both
   storefronts on the merge commit, nothing in progress).
3. **Merge freeze on `main`** for the rest of the migration and during every benchmark series:
   nothing is merged. This is the freeze that works with IaC. `config apply` deploys the
   branch's latest commit, so `main` must stay on the approved commit while stages are applied.
4. Snapshots prove it: `pnpm railway:deployments --save .railway/evidence/<date>/before.json`
   at the start, `--compare` that file at the end. Any redeploy fails the comparison.

Why not disconnect the GitHub trigger in the dashboard: it changes each service's `source`,
so the baseline plan would no longer be a no-op (expected; not tried against production) and
every proposal would fail the plan gate until it is reconnected. Use it only for a freeze in
which no stage is applied, and reconnect (branch `main`) before the next `pnpm
railway:plan-gate`. Stage 5 (`checkSuites`) makes autodeploys wait for green CI and keeps both
storefronts on one commit, but it does not stop them.

## Approval package (required per stage, before applying it)

The owner approval of discarding the demo database does **not** approve any of these stages.
For each stage, the operator presents and the owner approves:

1. **The exact plan**: `pnpm railway:plan-gate --file .railway/proposals/<stage>.ts --out-dir
.railway/evidence/<date>` → PASS, and the change table (it must equal the table above).
2. **Expected downtime**: stage 1 and 3 about 1–3 minutes without the API (a volume-backed
   deployment cannot overlap: the old one stops first; measured for stage 1: about 30 s, and
   the old deployment stopped as soon as the apply landed, before the build); 2 and 4 none (the storefronts'
   health check gates the switch); 5 none.
3. **Data loss**: stage 1 starts on an empty volume. **The current demo database (orders,
   accounts, sessions since the last API redeploy, 2026-11-26 04:13 UTC) is lost**, by owner
   decision. No later stage loses data (the volume keeps it).
4. **Services that redeploy**: the "Redeploys" column. Nothing else.
5. **Costs**: the volume is billed on storage used, $0.15 per GB-month; the Trial plan's maximum
   is 500 MB, so at most about $0.08 a month (the database is a few MB). No new service; CPU and
   memory limits are unchanged. Note that Trial credits expire 30 days after sign-up.
6. **Rollback**: per stage in [persistence](M9.3-TALADB-PERSISTENCE-VALIDATION.md#rollback) and
   [security](M9.3-API-SECURITY-VALIDATION.md#rollback). No rollback deletes the volume.
7. **No unrelated change**: the plan gate fails on any change not listed, any service
   deletion or replacement, a region, replica or limit change (an update may only touch the
   settings its proposal lists), a dropped volume, or a secret value in the file.

## Applying an approved stage

1. `main` is frozen on the approved commit; `pnpm railway:deployments --expect-sha <commit>` passes and is saved as the "before" snapshot.
2. `pnpm railway:plan-gate --file .railway/proposals/<stage>.ts` → PASS with the approved table.
3. `railway config apply --file .railway/proposals/<stage>.ts`, interactive, read the
   confirmation. Never `--yes` / `--confirm-destructive`.
4. Watch the deployment (`railway logs -s <service>`), then run the stage's live checks.
5. Fold it in, in one PR: set the flag in `CURRENT` (`.railway/railway.ts`), add the stage to
   `APPLIED_STAGES` (`scripts/railway/expected-production.mjs`), delete the proposal, update the
   docs' status. `pnpm railway:check` and `pnpm railway:plan-gate` (no-op) must pass.
6. Only then the next stage.
