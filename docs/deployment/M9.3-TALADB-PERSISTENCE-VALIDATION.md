## Decision: option A, a fresh database

The owner approved discarding the current Railway demo database. It is fictional demo data on
the API container's ephemeral disk, already reset by every API redeploy (the latest on
2026-11-26 at 04:13 UTC, a manual redeploy). No backup, copy, hot-copy or restore is made. The
volume starts empty and the API creates a new database on it. This replaces options B and C of
[TALADB-PERSISTENCE-MIGRATION.md](TALADB-PERSISTENCE-MIGRATION.md), and also its two-redeploy
`bootstrap.db` runbook: `TALADB_PATH` stays `/data/velasia.db`, so **one API redeploy**.

## Target

```text
@velasia/retailing-api   docker/Dockerfile.api, entrypoint docker/api/start.sh, 1 replica, iad
  └── volume velasia-api-data (500 MB, iad) at /data
        └── /data/velasia.db   (TalaDB, exclusive file lock, owned by uid 1000)
```

Variables the stage adds: `NODE_ENV=production`, `PORT=4010` (Railway's health check and
routing port), `RAILWAY_DOCKERFILE_PATH=docker/Dockerfile.api`, `RAILWAY_RUN_UID=0`,
`RAILWAY_DEPLOYMENT_DRAINING_SECONDS=15`. Already present and now effective:
`TALADB_PATH=/data/velasia.db`, `TALADB_REQUIRE_VOLUME=enabled` (inert under Railpack),
`RETAILING_API_HOST=::`, `RETAILING_API_PORT=4010`, `SHUTDOWN_TIMEOUT_MS=10000`. Deploy health
check `/health/ready`, timeout 120 s.

`RAILWAY_RUN_UID=0` is needed because Railway mounts a volume root-owned. Only `start.sh` runs
as root: it gives `/data` (and top-level files in it) to uid 1000, then `setpriv` drops to uid
1000 with no capabilities and `no_new_privs` before `exec`ing Node.js. Verified below.

## What the code guarantees (reviewed against the source)

| Requirement                         | Where                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Missing volume fails explicitly     | `start.sh`: `TALADB_REQUIRE_VOLUME=enabled` and `/data` not a mount point → JSON error, exit 1, before the API starts. There is no fallback path                                                                                                                                                                                                                 |
| `/data` writable by the API user    | `start.sh`, as root: `chown 1000:1000 /data` + `chmod 0700`; as uid 1000: refuses an unwritable directory with a message naming `RAILWAY_RUN_UID=0`                                                                                                                                                                                                              |
| One owner                           | TalaDB's exclusive lock (`src/db/client.ts`); a second opener fails "in use by another process". One replica (Railway also refuses replicas on a volume-backed service)                                                                                                                                                                                          |
| Migrations                          | `openDatabase` applies them, verifies every index, records the schema version, and refuses a file from a newer incompatible build                                                                                                                                                                                                                                |
| Existing data reopened, never reset | Nothing seeds, resets or deletes a database at startup; `start.sh` logs "opening the existing database"                                                                                                                                                                                                                                                          |
| Readiness                           | `GET /health/ready`: 200 only when TalaDB answers, migrations and indexes are verified, the ledger is rebuilt, recovery and session restore are done, and the API is not shutting down. Its body has status, latency, schema version and queue sizes, no path or configuration                                                                                   |
| Graceful shutdown                   | SIGTERM: readiness fails at once, the listener closes, in-flight requests finish (connections closed after their answer), queued TalaDB writes drain, shopping sessions are flushed, TalaDB closes, exit 0. Bounded by `SHUTDOWN_TIMEOUT_MS=10000` (then exit 1; commits are atomic). Railway's draining window (15 s) is longer, so SIGKILL never cuts it short |

## Local validation (implemented and tested locally)

`sh scripts/docker/validate-api-persistence.sh velasia-api:m93` on the image built from this
branch (`docker build -f docker/Dockerfile.api -t velasia-api:m93 .`), with stage 1's variables
and a new, empty, root-owned Docker volume (`volume-nocopy`). **31 passed, 0 failed**:

1. **Guard**: no volume, as root and as uid 1000 → exit 1, "… is not a mounted volume …"; the
   API never opened a database.
2. **Ownership**: root-owned volume without `RAILWAY_RUN_UID=0` → exit 1, the message names the
   fix. With it: "database directory /data given to uid 1000"; PID 1 is uid 1000, `CapEff` 0,
   `NoNewPrivs` 1; `/data` is a mount point; `velasia.db` is owned by uid 1000.
3. **Fresh database**: "no database at /data/velasia.db yet: the API creates an empty one";
   `/health/ready` 200 with schema version 3; the body names no path, file or token.
4. **One owner**: a second API container on the same volume exits 1 "in use by another
   process"; the first stays ready.
5. **SIGTERM**: `docker stop -t 15` → exit code 0, "shutdown complete", in about 1 s.
6. **Restart and redeploy**: `docker start` and a new container on the same volume both log
   "opening the existing database at /data/velasia.db"; the disposable record (a shopping session
   with a synthetic search) is still there; same schema version.

Also checked: the image's history and environment contain no token or secret.
Not reproducible locally: Railway's health checker, its volume mount, and its stop sequence.

## Runbook (after approval of stage 1)

Preconditions: the [approval package](M9.3-RAILWAY-RELEASE-READINESS.md#approval-package-required-per-stage-before-applying-it)
for stage 1 is approved; the M9.3 code is merged and deployed (the merge event); `main` is
frozen; no benchmark runner exists.

1. Evidence: `pnpm railway:deployments --save .railway/evidence/<date>/before-stage1.json`.
2. `pnpm railway:plan-gate --file .railway/proposals/api-persistence.ts --out-dir
.railway/evidence/<date>` → PASS, 9 changes (1 create, 8 updates, 0 destructive).
3. `railway config apply --file .railway/proposals/api-persistence.ts` (interactive).
   **Expected downtime: about 1–3 minutes without the API** (Docker build first, while the old
   deployment still serves; then the old deployment stops before the volume-backed one starts).
   The storefronts stay up: prerendered pages work; search and booking say "temporarily
   unavailable" until the API is back.
4. Startup logs (`railway logs -s @velasia/retailing-api`): "given to uid 1000", "no database
   at /data/velasia.db yet", "orders database ready" with `schemaVersion`. The deployment
   becomes active only after `/health/ready` passes.
5. Storefronts: `/api/internal/health/ready` 200 on both domains; NextRS logs its new API
   addresses (`railway logs -s @velasia/web-nextrs --dns`), inside its allowlist.
6. **Persistence check** (disposable data only, never a real person or card): create one demo
   booking through a storefront with a synthetic traveller and the simulated payment, and record
   its reference (`VEL-…`) in the private evidence only. Then `railway restart -s
@velasia/retailing-api` → the booking is retrievable and the log says "opening the existing
   database". Then one redeploy of the same commit → retrievable again.
7. **One owner**: one active deployment (`pnpm railway:deployments`), one "orders database
   ready" line per deployment, no lock errors.
8. Record actual downtime (from the deployment timestamps) and the results in this document.
9. Fold stage 1 into the baseline (release readiness, "Applying an approved stage", step 5).

## Rollback

- Before step 3: nothing changed.
- After it: roll back the API deployment in the dashboard (Deployments → the last good one →
  Rollback). The volume stays attached and its database untouched. **Never apply the M9.2
  baseline (`apiPersistence: false`) once the volume exists**: in a whole-project file an
  omitted resource is deleted, so its plan deletes the volume and the database with it. The
  plan gate refuses that plan ("desired graph drops live volume"). A rollback of the build
  itself (back to Railpack) would be a separate proposal that keeps the volume declared.
- Never delete the volume as a rollback step: deleting a volume also deletes its backups.
- A failed start (guard, permissions, lock) never becomes active: the health check keeps the old
  deployment serving.

## After the migration

Backups are cold copies (`db-tool backup`) with the API stopped, in a maintenance window, now
possible because the volume outlives the container. Railway volume backups can be enabled where
the plan offers them (restorable only into the same project and environment).
